Inside mterm

How mterm is built: the two processes, the protocol over the socket, the replay buffer, the tracking of the terminal modes, the status bar, PTY handling, the tests and the known limitations. For anyone who has to modify it or understand why it behaves the way it does.

Version 1.0 Language Go 1.24, standard library only System Linux

Overview

What this manual covers, the principles mterm rests on and where everything is in the code.

What this manual covers

Everyday use is in the User Manual. This one describes the inner workings: everything you need to fix a defect or add a feature without breaking the properties that make mterm useful. The reasons behind the fundamental choices are in decisions and history.

Principles

⇆

No emulation

The program's output reaches the real terminal byte for byte. mterm keeps no model of the screen and does not rewrite sequences.

+

Additions only in between

The only bytes generated by mterm are the status bar, the window overlay, the restoring of modes and the cleanup on window switch.

1

One binary, zero dependencies

Only Go's standard library, CGO_ENABLED=0: a static executable that runs on any Linux of the same architecture.

✓

Verified live

Every property is covered by an end-to-end test that drives the real executable through a real PTY.

Build

The build is a single line, CGO_ENABLED=0 go build -trimpath -ldflags "-s -w" -o mterm ., wrapped by the Makefile:

CommandEffect
makeRebuilds ./mterm (static, linux/amd64).
make testFirst tools/check-docs.py (on the committed executable), then rebuilds and runs go vet, gofmt and all the end-to-end tests. Stops at the first error.
make e2eOnly the end-to-end tests, on the executable as it is: Go is not needed.
make docs-checkOnly the manual checks.
make distdist/mterm-linux-amd64, dist/mterm-linux-arm64 and SHA256SUMS.
make installCopies ./mterm into $(PREFIX)/bin, normally ~/.local/bin.

The Makefile uses the go found in PATH or, failing that, ~/.local/go/bin/go. go.mod requires Go 1.24, the version of Debian 13's golang-go package: on the tablet apt is enough.

CI and releases

On every push to main and every pull request GitHub Actions runs make test and make dist on Ubuntu 24.04 (check-docs.py, inside make test, checks that the committed executable exists and carries the right version). On a v* tag it also publishes a release with the two binaries and the SHA-256 checksums; the notes are the message of the annotated tag. To release:

  1. Update the version in help.go ("mterm 1.0"), README.md, docs/index.html and in the two manuals. make test checks that they match.
  2. make and commit ./mterm too.
  3. git tag -a v1.1.0 -m "mterm 1.1.0: …what's new…"
  4. git push origin main v1.1.0

Recovery and backup

The repository is designed so that a git clone is enough to get everything back: mterm has no personal files, and the ready-made executable is committed. tools/setup-dev.sh recreates the only thing a clone does not bring, the local git identity (GitHub noreply address, to keep the personal one out of the public history), and lists the missing packages. tools/backup.sh DIR writes a verified git bundle --all, which can be cloned without a network.

Architecture

Two roles in the same executable, connected by a UNIX socket.

The processes

flowchart LR
  TERM["real terminal"] <-->|"stdin / stdout<br/>raw mode"| CLI["client<br/>mterm attach"]
  CLI <-->|"UNIX socket<br/>NAME.sock"| DAE["daemon<br/>mterm __daemon NAME"]
  DAE <-->|"PTY master"| P0["window 0<br/>$SHELL or command"]
  DAE <-->|"PTY master"| P1["window 1<br/>$SHELL"]
  DAE -.->|"log"| LOG[("NAME.log")]
  • Daemon (runServer): one per session. It is the same executable launched as mterm __daemon NAME [command…], a hidden subcommand. It owns the PTYs, the child processes, the replay buffers, and listens on the socket. It has no terminal: stdin/stdout/stderr on /dev/null, new POSIX session (Setsid), so it survives the closing of the terminal that created it.
  • Client (attach): the process the user sees. It puts the terminal into raw mode and acts as a pipe. There is at most one connected per session.
  • Short commands (ls, kill): they open the socket, ask one question, close.

Life cycle of a session

sequenceDiagram
  participant U as mterm new NAME
  participant D as daemon
  participant S as shell
  U->>D: exec __daemon NAME (Setsid, fds on /dev/null)
  D->>D: Listen NAME.sock, opens the log
  D->>S: openPTY + startShell
  loop up to 2 s
    U->>D: ping 'P'
    D-->>U: 'o'
  end
  U->>D: 'A' (attach)
  U->>D: 'S' rows columns
  D-->>U: modes + clear + replay + 'M' metadata
  Note over U,D: pipe: 'D' in both directions
  S--xD: the shell exits (EOF on the master)
  D->>D: closeWindow, last one: shutdown
  D--xU: socket closed: [sessione terminata]

cmdNew refuses a name that is already alive, launches the daemon with exec.Command(os.Executable(), "__daemon", …), releases the process and polls the socket every 10 ms, at most 200 times. As soon as the daemon answers the ping, it behaves like attach. If it does not answer, the error points to the log.

The daemon ends in shutdown (guarded by sync.Once): it kills the children, closes the listener, removes the socket, os.Exit(0). It gets there when the last window closes, with the command K, or with SIGTERM/SIGHUP. Seeing the socket close, the client prints [sessione terminata] (session ended).

Paths and names

sockDir is $XDG_RUNTIME_DIR/mterm, or /tmp/mterm-UID if the variable is missing, created with permissions 0700. Inside: NAME.sock and NAME.log. Protection between users lies entirely in the folder permissions: the socket has no authentication.

isAlive is the liveness test: it connects (500 ms timeout), sends P, expects o. It does not disturb an attached client. cmdList uses it on every *.sock and removes those that do not answer. pickName picks the smallest integer not used by a .sock. mustName rejects names that are empty or contain /, a space or a tab.

The protocol

A minimal, asymmetric binary protocol over the UNIX socket.

The first byte: the mode

ByteMeaningReply
PPing, used by isAlive.o, then close.
KKill: ends the session.o, then shutdown.
AAttach: from here on, frames in both directions.Daemon frames.

Frames from the client to the daemon

'S' + rows(uint16 BE) + columns(uint16 BE)    size (rows already reduced by 1 for the bar)
'D' + length(uint16 BE) + data                input for the current window (max 65535 per frame)
'C'                                           create a window
'n' / 'p'                                     next / previous window
'g' + id(uint16 BE)                           go to the window with that id
'x'                                           close the current window
'b'                                           request the replay buffer (reply: frame 'B')

The daemon reads them with parser.feed, a state machine (stType, stSize, stDlen, stData, stGoto) that copes with frames split across several reads. The data of a D frame is written to the PTY master piece by piece, as it arrives. Bytes of unknown type are ignored.

Frames from the daemon to the client

A single format: type(1) + length(uint32 BE) + payload, written by push under the mutex cmu.

TypePayload
DRaw output of the current window, or the restore package (modes + clear + replay).
MText metadata: first line current_id\talt (alt = 1 if the window is on the alternate screen), then one line id\ttitle per window.
BCopy of the current window's replay buffer, in reply to b.

If a write to the client fails, push drops that client at once: the windows' output must never stay blocked on a dead connection.

The daemon

server.go: windows, buffers, modes, restore.

Windows

A window (win) consists of: id, PTY master, exec.Cmd, title, alt flag, replay buffer, map of modes, tail for split sequences. The server keeps the list wins, the current index cur and the next id nextID, which only ever grows: ids are not reused.

The title is the base name of the command or of $SHELL, fixed at creation (titleFor). The first window uses the command passed after --; createWindow (frame C) always starts the shell. closeWindow closes the master, kills the process, removes the window, realigns cur and repaints the new one; if it was the last one it calls shutdown.

Reading the windows

Each window has its own goroutine winReader, which reads the master in 32 KiB blocks always, even when the window is not visible or nobody is attached: that way a program is never left blocked on a write. For each block, under s.mu: it updates the modes (scanModes), appends it to the buffer (record); then, if the window is the current one, forwards it with push('D') and, if the alternate-screen state has changed, sends the metadata again. A read error (the shell has exited) closes the window. A panic is recorded in the log with the stack and closes only that window.

Replay buffer

Each window keeps the last bytes of output, up to bufMax = 5 MiB. Once the threshold is exceeded, record keeps only the last half (bufKeep) and moves the cut forward to the first ESC, so as not to restart from the middle of an escape sequence.

The buffer is used to restore the screen on reattach and on window switch without depending on the program redrawing itself on SIGWINCH: an idle shell or a TUI that redraws only partially (Claude Code) would otherwise come back with an empty screen. It is not emulation: they are the same bytes, replayed. Cost: up to 5 MiB of memory per window.

Tracked DEC modes

Some private terminal modes, if left on by one window, spoil the others: the typical case is the mouse tracking of a TUI, which delivers every mouse movement to a shell as random characters. The daemon therefore keeps, for each window, the state of a fixed set of modes (trackedModes): cursor visible (25), the various mouse modes and encodings (9, 1000–1006, 1015, 1016), focus events (1004), bracketed paste (2004), plus the alternate screen (47, 1047, 1049 → alt).

scanModes looks in the output for the sequences ESC [ ? n;n… h|l and updates the state. The last 32 bytes of each block (tailMax) are re-examined together with the following block, so that a sequence split across two reads is not lost; applying it twice is harmless because h/l set a state, they do not toggle it.

appendModes produces the sequences that bring the real terminal to the window's state, in the fixed order trackedOrder and preceded by ?1049h/l. They are emitted before the replay: they turn off what the previous window had turned on and turn back on what is needed even if the original sequence has dropped out of the buffer because of the cut.

Screen restore

repaint(w, cols, rows) sends the client a single D frame with: the window's modes, ESC [H ESC [2J (clears the visible part, not the scrollback: no 3J), the replay buffer. Then it sends the metadata and «jiggles» the PTY size (rows-1 and then rows): the program receives a SIGWINCH in any case and TUIs realign themselves if the terminal has changed size in the meantime. It is used by activate (window switch), createWindow, closeWindow and the first resize after an attach.

Attach and sizes

serveClient replaces the previous client, closing its connection (the «eviction»: the old client sees the socket close, checks that the session is still alive and prints sessione ripresa altrove (session resumed elsewhere)). The restore does not happen at once: needPaint stays pending until the first S frame, when the new terminal's dimensions are known. resize applies the size to all windows, not only to the current one.

Concurrency

Two mutexes: mu protects the state (windows, current one, sizes, client, buffers, modes); cmu serialises writes to the socket, so frames from different goroutines do not get mixed. Rule: push must never be called while holding mu, because it takes it itself. Functions copy what they need under mu and release it before writing.

Log and signals

The daemon has no terminal: the log NAME.log (opened with O_TRUNC, hence emptied at every new session with the same name) is the only place where it can report startup, attaches and detaches, failures and panics (with the stack, from winReader and serveClient). SIGTERM and SIGHUP lead to shutdown, so the socket is not left orphaned.

The client

client.go: the pipe, the keys, the bar.

Startup

attach connects in mode A, puts stdin into raw mode (enterRaw: no echo, no canonical mode, no keyboard signals, no output translation), clears the screen, sets the scrolling region, sends the size and draws the bar. Then it launches three goroutines and waits on endCh for the reason it ended: detached (key or stdin closed) or session (socket closed by the daemon). A SIGWINCH handler sends the size again and redraws.

The three loops

  • readLoop reads the frames from the socket and puts them on a channel.
  • outputLoop consumes them. For speed it coalesces: after one frame it drains all those already queued and does a single write to stdout. An M frame forces a flush first (to keep the order) and redraws the bar; a B frame is saved to a file. The bar is not redrawn in the middle of the output: a timer redraws it 12 ms after the stream stops, and the clock tick (1 s) only if there has been no output in the last 40 ms. That way the app's sequences are not broken up and there is no flicker.
  • inputLoop reads stdin and recognises the Ctrl-a prefix (0x01). The rest goes to the daemon in D frames; commands become control frames. An unknown key after the prefix is forwarded together with the prefix. If the overlay is open, keys go to handleOverlayKey.

Status bar and scrolling region

The bar takes up the last physical line. To the daemon the client declares rows-1, so the program never writes there; and it sets the scrolling region ESC [1;rows-1 r, so that a shell wrapping at the bottom scrolls above the bar instead of dragging it along. With fewer than 3 lines the bar is disabled and the program receives all the lines.

Many programs reset the scrolling region when they exit. That is why drawBar reasserts it at every redraw when the window is on the normal screen; on the alternate screen it does not touch it, so as not to interfere with the app. The alt state comes from the daemon in the metadata. The drawing is wrapped in Synchronized Update Mode (?2026h…?2026l, ignored by terminals that do not support it) and between DECSC/DECRC (ESC 7/ESC 8), which save and restore the cursor's position and attributes.

buildBar composes: ⬢ name, the window ids (the current one in reverse video), and on the right user@host hh:mm:ss or, for 4 seconds, the message from setFlash. The result is exactly as wide as the terminal; if it does not fit, the right-hand part is removed first and then it is truncated.

The window overlay

Ctrl-a " opens a list drawn by the client over the screen. While it is open, incoming D output is discarded (not queued). On closing, whether with a choice or with Esc, the client sends a g: even with the current id, this triggers a repaint that rebuilds the screen from the buffer, including what had been discarded.

Cleanup on detach

cleanup leaves the user's terminal tidy: if the window was on the alternate screen it exits with ?1049l; it turns off mouse, focus and bracketed paste; shows the cursor again; resets the attributes; removes the scrolling region and erases the bar. Then restoreTerm restores the terminal settings.

Saving and conversion to text

Ctrl-a s sends b; the daemon replies with a copy of the buffer in a B frame; saveBuffer writes into the client's current folder mterm-SESSION-wID-hhmmss.raw (raw bytes) and .txt (via plainText). The name of the session goes through sanitizeName.

plainText is not an emulator: it strips escape sequences (escLen recognises CSI, OSC, DCS/SOS/PM/APC up to BEL or ST, character set designation, ESC plus one byte) and applies minimal line logic: \r returns to the start of the line and overwrites, backspace, tabs every 8, trailing spaces removed, other controls ignored. Progress bars and rewritten prompts are cleaned up; the vertical cursor movements of TUIs are not.

PTY and terminal

The system calls, without external libraries.

Opening a PTY

openPTY opens /dev/ptmx with O_NOCTTY, unlocks the slave (TIOCSPTLCK = 0x40045431) and reads its number (TIOCGPTN = 0x80045430), returning the master and /dev/pts/N. The two constants are those of Linux's generic family, valid on amd64 and arm64 (not, for example, on mips or powerpc).

Starting the program

startShell opens the slave with O_NOCTTY (the daemon must not take it as its own controlling terminal, otherwise the child could not) and starts the command with stdin/stdout/stderr on the slave, Setsid and Setctty on descriptor 0: the child becomes leader of a new session with the slave as its controlling terminal, so job control and Ctrl-C work. The environment is that of the daemon, that is, of whoever created the session: TERM included, left untouched.

Sizes

setWinsize does TIOCSWINSZ on the master: the kernel sends SIGWINCH to the foreground group. termSize reads the size from stdout, stderr, stdin or /dev/tty, falling back to 80×24.

Built-in guide

help.go holds the contents only once: helpSections (commands and keys), helpExamples, descrizione. From there come both the man-style page (buildHelp) and the TUI tabs (buildTabs in tui.go). displayHelp chooses: plain text without colours if stdin or stdout is not a terminal; otherwise the TUI (alternate screen, raw mode, 44×10 minimum); if the TUI does not start, the man page through $PAGER, less -R -F -X or more.

The version is in the last line of the man page, "mterm 1.0": it is the value that check-docs.py compares with the manuals, the README and the string inside the committed executable.

Tests

End-to-end tests on the real executable, through a real PTY.

How they work

Each test is a Python 3 script that uses only the standard library: pty.fork() launches ../mterm inside a PTY of known size, sends keys as a user would and reads what mterm writes to the terminal, looking for exact bytes (escape sequences included). Each check prints OK or FALLITO (failed); the exit status is 1 if at least one has failed. The environment is isolated: XDG_RUNTIME_DIR points to a test folder (make e2e uses /tmp/mterm-test-xrt), SHELL=/bin/sh, TERM=xterm-256color.

There are no Go unit tests: every property that matters concerns the behaviour seen from a terminal, and is verified that way.

Documentation checks

tools/check-docs.py, run by make test and by the CI, fails if:

  • an entry of helpSections has, in the reference section of the User Manual, no <dt data-help="…"> with exactly the same text, or vice versa;
  • a .go file is missing from the file map, or the line counts given differ by more than 10% from the real ones;
  • a test in tests/ is missing from the table of tests;
  • ./mterm is missing, is not an x86-64 ELF or does not contain the version from help.go;
  • the version does not match in README.md, docs/index.html and the two manuals;
  • an #anchor link in the manuals points to a non-existent id.

Conventions

  • Italian everywhere, except the manuals: messages, comments, built-in guide, commit messages; these two manuals are in English.
  • No dependencies: standard library only; system calls are made with syscall.
  • No reinterpretation of the output: if a new feature requires understanding what is on the screen, it must be rethought. Reading the output to track a state (as scanModes does) is allowed; modifying it is not.
  • Own bytes only between one burst and the next: no client writes in the middle of a stream from the app.
  • Every fix for a visible defect has its own end-to-end test, which fails without the fix.
  • gofmt and go vet clean; errors for the user via fatal, prefix mterm:, status 1.

Known limitations and open issues

Known limitations

  • Windows beyond 9: Ctrl-a plus a digit and the overlay accept a single character, and ids are not reused; from window 10 onwards they can only be reached with n/p.
  • new without a terminal: the daemon starts, then attach fails on enterRaw with status 1; the session stays alive and detached. Useful from scripts, but the exit code is misleading.
  • Reserved names: a session named like a command (ls, n, help…) cannot be reached with mterm NAME.
  • Fixed titles: a window's title is the name of the program started, it does not follow the titles set by the app.
  • Replay after a resize: the replayed bytes were written for the old width; TUIs realign on SIGWINCH, shell text does not.
  • Memory: up to 5 MiB of buffer per window; older history is not replayed.
  • Folder permissions: os.MkdirAll(dir, 0700) does not correct the permissions if the folder already exists; with the fallback in /tmp another user could have created it first.
  • Architectures: the ioctl constants in pty_linux.go hold for amd64 and arm64 (and the others of the generic family), not for all of them.
  • Log: started over at every session with the same name; the log of a crashed session must be read before recreating it.

Ideas for the future

  • Choosing windows beyond 9 in the overlay (more digits or arrows).
  • Renaming sessions and windows; titles from the app's OSC sequences.
  • mterm new -d to create a detached session without an error.
  • Checking the owner and permissions of the socket folder.

Glossary

PTY
Pseudo-terminal: a kernel master/slave pair. The program uses the slave as if it were a terminal; whoever holds the master reads what it writes and sends it input.
Raw mode
Terminal setting in which every key reaches the program immediately, without echo or line processing.
DEC private mode
Terminal setting turned on with ESC [ ? n h and turned off with ESC [ ? n l.
Alternate screen
The terminal's second screen, without scrollback, used by full-screen programs (mode 1049).
Scrolling region
Range of lines within which the terminal scrolls text (ESC [ top ; bottom r).
Synchronized Update Mode
Mode 2026: the terminal shows everything between switching it on and switching it off in one go.
SIGWINCH
Signal that tells a program that the size of its terminal has changed.
Git bundle
A file that contains a complete git repository, from which you can clone without a network.
